Câu trả lời tốt nhất

nói trong khoảng 45 giây

Cache-aside (phổ biến nhất): ứng dụng đọc cache trước; trượt thì đọc database rồi ghi vào cache với TTL; khi ghi, cập nhật database rồi xoá khoá trong cache (không cập nhật) để lần đọc sau nạp lại. Read-through/write-through: thư viện hoặc lớp cache tự đọc/ghi database thay ứng dụng — ghi đồng bộ cả hai, cache luôn mới nhưng ghi chậm hơn. Write-behind: ghi vào cache rồi đẩy xuống database bất đồng bộ — ghi rất nhanh nhưng mất dữ liệu nếu cache chết; không dùng cho tiền. Dữ liệu cũ xuất hiện khi: quên xoá khoá ở một đường ghi nào đó; race — một request đọc giá trị cũ từ database, ghi vào cache sau khi request ghi đã xoá khoá; hoặc database bị sửa trực tiếp. Giảm thiểu: TTL làm lưới an toàn; xoá khoá theo sự kiện thay đổi (CDC); với dữ liệu nhạy cảm, không ra quyết định dựa trên cache — số dư hiển thị thì được, kiểm tra số dư khi chuyển tiền thì phải đọc database.

Trả lời đầy đủ

Cache-aside

public Product get(long id) {
    String key = "product:" + id;
    Product cached = redis.get(key);
    if (cached != null) return cached;                       // hit
    Product p = repo.findById(id).orElseThrow();              // miss -> DB
    redis.set(key, p, Duration.ofMinutes(10).plusSeconds(rnd.nextInt(60)));   // TTL + jitter
    return p;
}

@Transactional
public void update(Product p) {
    repo.save(p);
    afterCommit(() -> redis.delete("product:" + p.id()));    // xoá SAU khi commit
}

So sánh

Chiến lược Đọc Ghi Rủi ro
Cache-aside trượt lần đầu DB rồi xoá cache dữ liệu cũ do race
Read/Write-through cache lo việc nạp ghi đồng bộ cả hai ghi chậm hơn
Write-behind nhanh ghi cache, DB sau mất dữ liệu khi cache chết
Refresh-ahead luôn nóng — nạp cả dữ liệu không ai đọc

Race kinh điển

A đọc DB (giá trị cũ v1) ──────────────────────────> A ghi v1 vào cache  (cũ!)
            B ghi DB v2 -> B xoá cache

Giảm thiểu: TTL ngắn cho dữ liệu hay đổi; xoá trễ lần hai (xoá lại sau vài trăm ms); hoặc ghi kèm version và chỉ chấp nhận version mới hơn.

Nên cache gì

Nên Không nên
danh mục, cấu hình, hồ sơ ít đổi dữ liệu dùng để quyết định tiền
kết quả tính toán đắt dữ liệu mỗi người đọc một lần
phiên đăng nhập dữ liệu cá nhân nhạy cảm mà không có mã hoá/TTL

Sẽ bị hỏi tiếp

  • Vì sao xoá thay vì cập nhật cache khi ghi? Hai request ghi đồng thời có thể cập nhật cache theo thứ tự ngược với database; xoá thì lần đọc sau luôn lấy giá trị từ database.
  • Xoá cache trước hay sau khi commit? Sau — xoá trước thì request đọc chen vào có thể nạp lại giá trị cũ trước khi transaction commit.
  • Đo hiệu quả cache thế nào? Tỉ lệ hit, độ trễ p99 khi hit/miss, tải database trước và sau; hit rate thấp thì cache chỉ thêm độ phức tạp.

Bẫy thường gặp

  • Cập nhật cache trước khi commit — transaction rollback, cache giữ giá trị không tồn tại.
  • Không TTL — một lần quên xoá là sai vĩnh viễn.
  • Write-behind cho dữ liệu tài chính — mất giao dịch khi cache chết.

Thực tế trong dự án của tôi

Ngữ cảnh dựng từ các hệ thống bạn đã tham gia (vai trò chính của bạn là frontend). Tình huống điển hình là tình huống hay gặp khi thiết kế hệ thống ngân hàng, bảo hiểm do app biên soạn để luyện cách kể; số liệu là ví dụ minh hoạ. Ghi rõ phần bạn tự làm và phần chỉ phối hợp.

Ngữ cảnh: frontend ngân hàng A cache danh mục; backend có thể cache danh mục ít đổi.

  • Đã làm: chọn cache-aside cho danh mục, đặt TTL và làm mới khi đổi.
  • Kết quả: trả lời có ví dụ.

Tình huống điển hình: Thông tin sản phẩm vay được cache theo kiểu cache-aside với TTL 1 giờ; khi bộ phận sản phẩm đổi lãi suất, app vẫn hiện lãi suất cũ thêm gần 1 giờ, gây khiếu nại. Đội giữ cache-aside nhưng xoá khoá ngay sau khi cập nhật database thành công, TTL giảm còn 10 phút làm lưới an toàn; dữ liệu cần chính xác tuyệt đối như số dư thì không cache. Thay đổi lãi suất hiển thị trong vài giây.
