Phỏng vấn DevOps — Junior

Phần 4, level Junior — 76 câu lý thuyết DevOps theo chủ đề (Linux, mạng, Git, Docker, CI/CD, Kubernetes, observability, cloud và IaC, bảo mật, vận hành), 9 tình huống sự cố trả lời theo khung 5 bước, 5 câu hành vi khi chuyển ngành, 5 bài thực hành (có một bài take-home) và một bài thiết kế pipeline ngân hàng; mỗi câu có mức ưu tiên, trả lời ngắn, giải thích sâu, lệnh/cấu hình, lỗi hay gặp và câu hỏi đào tiếp.

Level đầu tiên của Phần 4 — chuẩn bị phỏng vấn trong lộ trình DevOps từ con số 0, tương ứng giai đoạn 1–8 (khoảng tháng 1–10). Level sau: Middle · Senior.

Ở level Junior, người phỏng vấn kiểm tra ba thứ: nền Linux và mạng chắc (hầu hết JD ngân hàng ghi đầu tiên), làm được việc hằng ngày với Docker, CI/CD, Kubernetes, và cách gỡ lỗi có hệ thống — không đoán, đi từng bước, nói được lệnh nào cho kết quả gì. Với người từ Frontend chuyển sang, họ thường mở đầu bằng "DevOps là gì" và "vì sao bạn chuyển" — hai câu này có ở mục CI/CD và mục Hành vi.

Mỗi câu mở ra có đủ: ⭐ trả lời ngắn (đoạn nói trong khoảng 45 giây), 📖 giải thích sâu (cơ chế, vì sao), 💻 lệnh hoặc cấu hình, ⚠️ lỗi hay gặp, 🔁 câu hỏi đào tiếp. Dòng in nghiêng dưới mỗi câu là ý chính để ôn nhanh. Mở câu, tự trả lời thành tiếng trước rồi mới xem đáp án.

Mức ưu tiên: Bắt buộc phải trả lời trôi · Nên biết hay bị hỏi, trả lời được là điểm cộng · Nâng cao dành cho người muốn nổi bật.

Thuật ngữ mới ở level này

Thuật ngữ Nghĩa ngắn
Runner, agent Máy chạy các job của pipeline
Artifact Sản phẩm của bước build, truyền sang bước sau và được lưu lại
Stateful firewall Firewall nhớ kết nối, tự cho gói trả lời đi qua
SELinux context Nhãn của file, process, cổng mà SELinux dùng để quyết định cho phép
Probe Kiểm tra định kỳ để Kubernetes biết pod còn sống, đã sẵn sàng chưa
Reconcile Vòng lặp kéo trạng thái thật về khớp trạng thái khai báo
IaC state Bản đồ của Terraform giữa code và tài nguyên thật
SLI, SLO Chỉ số đo trải nghiệm người dùng; mục tiêu cho chỉ số đó

Qua cửa level Junior

  • ○ Trả lời thành tiếng mọi câu Bắt buộc, mỗi câu ≤ 1 phút, không nhìn đáp án.
  • ○ Trả lời 4 tình huống Bắt buộc theo khung 5 bước, nêu được lệnh cụ thể ở từng bước.
  • ○ Làm xong bài take-home trong ≤ 6 giờ; một người khác clone và chạy được chỉ bằng README.
  • ○ Vẽ pipeline CI/CD cho ứng dụng ngân hàng trên bảng trong 20 phút, có môi trường, cổng duyệt, kho artifact nội bộ, rollback.
  • ○ Dự án portfolio 1–4 có README đủ 8 mục (xem Portfolio, chứng chỉ, CV).

Tài liệu học cho level này

Level Junior của phỏng vấn trải trên giai đoạn 1–8, nên dùng cả hai mục Newbie và Junior của trang tài liệu. Học chính theo thứ tự:

  1. Linux Upskill Challenge ✅ và The Linux Command Line ✅ — nền Linux.
  2. High Performance Browser Networking ✅ — TCP, TLS cho dân web.
  3. Docker docs — Get started ✅ — Dockerfile tốt, Compose.
  4. GitLab CI/CD YAML reference ✅ và Jenkins — Pipeline ✅ — trùng công cụ ở dự án.
  5. Kubernetes Tutorials ✅, Killercoda ✅, learnk8s — Troubleshooting deployments ✅ — Kubernetes và gỡ lỗi.
  6. devops-exercises ✅ — tự kiểm tra trước buổi phỏng vấn.

Danh sách đầy đủ, phần cần đọc: Tài liệu DevOps — Newbie · Junior.

Linux

  • ○ Bắt buộc Đọc log, tìm lỗi nhanh trên server — tail -f, less, grep, awk, pipe, exit code?journalctl -u cho service; awk + sort | uniq -c | sort -rn để xếp hạng lỗi; CI chỉ đọc exit code.Lệnh Linux hằng ngày của developer trên server
  • ○ Bắt buộc Đọc -rwxr-x---, chmod 640; ứng dụng báo "Permission denied" thì kiểm tra gì?User của process, quyền từng thư mục trên đường dẫn (namei -l), owner/mode, rồi tới SELinux; không chạy ứng dụng bằng root.Quyền file trên Linux
  • ○ Bắt buộc Chạy ứng dụng lâu dài trên Linux thế nào — vì sao systemd thay vì nohup … &?Unit file: user riêng, Restart=on-failure, biến môi trường, giới hạn tài nguyên; log vào journal; SIGTERM để tắt an toàn.Process, signal và systemd trên Linux
  • ○ Nên biết Server RHEL: Nginx trả 403/502 dù quyền file đúng — vì sao, sửa thế nào?SELinux Enforcing: sửa nhãn bằng semanage fcontext + restorecon, bật httpd_can_network_connect; không setenforce 0.Server RHEL ở ngân hàng
  • ○ Nên biết Khi nào bỏ Bash, chuyển sang Python cho script vận hành?JSON, HTTP, xử lý lỗi theo trường hợp, dài quá vài chục dòng; subprocess dạng danh sách, timeout mọi lời gọi mạng, exit code đúng.Bash hay Python cho script vận hành
  • ○ Nên biết df báo đầy mà du không thấy file lớn?File đã xoá nhưng process còn mở: dung lượng chỉ được trả khi process đóng file; tìm bằng lsof.Tình huống: df báo đĩa đầy 100% nhưng du cộng lại chỉ 40%
  • ○ Nâng cao Server chậm — bắt đầu điều tra từ đâu?USE method cho CPU, bộ nhớ, đĩa, mạng; load average trên Linux đếm cả process chờ I/O.Tình huống: server chậm, load average 40 trên máy 8 core

Mạng

  • ○ Bắt buộc TCP khác UDP thế nào; bắt tay ba bước; "refused" khác "timeout"?TCP tin cậy, có thứ tự; UDP gửi gói độc lập; refused = tới máy nhưng không ai nghe, timeout = gói bị chặn hoặc mất.TCP và UDP, bắt tay ba bước, cổng; 'connection refused' khác 'timeout' thế nào; keep-alive, TIME_WAIT; HTTP/1.1, HTTP/2, HTTP/3 khác nhau ở tầng vận chuyển
  • ○ Bắt buộc DNS hoạt động thế nào; vì sao đổi bản ghi rồi mà chưa có hiệu lực?Resolver → root → TLD → authoritative; kết quả được cache theo TTL; kiểm tra bằng dig +trace.DNS hoạt động thế nào
  • ○ Bắt buộc Gõ URL rồi Enter — chuyện gì xảy ra tới khi trang hiện ra?DNS → TCP → TLS → HTTP qua CDN/load balancer → ứng dụng → trình duyệt render; mỗi chặng có công cụ debug riêng.Điều gì xảy ra khi gõ https://ebank.example.vn vào trình duyệt
  • ○ Bắt buộc SSH bằng khoá, ssh-agent, vào server qua bastion?ssh-keygen -t ed25519, authorized_keys, ProxyJump; tắt đăng nhập mật khẩu; ~/.ssh 700, khoá riêng 600.SSH cho developer
  • ○ Bắt buộc Mở đúng cổng cho đúng nguồn — ufw, firewalld, security group, network ACL?Mặc định chặn chiều vào; firewall Linux và security group là stateful, network ACL thì không; Docker publish port đi vòng qua ufw.Firewall trên Linux và cloud
  • ○ Nên biết TLS handshake, chuỗi chứng chỉ, SNI?Client gửi SNI; server gửi chứng chỉ kèm chứng chỉ trung gian; thiếu trung gian là lỗi hay gặp; xem bằng openssl s_client -showcerts.TLS và chứng chỉ
  • ○ Nên biết Reverse proxy khác load balancer; L4 khác L7; 502 khác 504?Proxy kết thúc TLS, định tuyến, cache; load balancer chia tải cho instance khoẻ; 502 upstream hỏng, 504 upstream quá chậm.Reverse proxy và load balancer
  • ○ Nâng cao Ứng dụng lỗi kết nối database nhiều nhất lúc ít người dùng — vì sao?Kết nối nhàn rỗi bị firewall/NAT giữa đường xoá mà không báo; pool lấy phải kết nối chết.Tình huống: service A gọi service B lúc được lúc 'connection reset' hoặc treo đúng 60 giây

Git

  • ○ Bắt buộc Ba vùng của Git: working tree, index, repository?add chép vào index, commit lưu index thành commit; restore lấy lại từ index hoặc commit.Ba vùng của Git
  • ○ Nên biết Branch thực chất là gì; HEAD và detached HEAD; stash?Branch là con trỏ có tên tới một commit nên tạo nhánh rất rẻ; detached HEAD khi HEAD trỏ thẳng vào commit.Branch thực chất là gì, HEAD và detached HEAD
  • ○ Nên biết fetch, pull, pull --rebase khác nhau; origin/main là gì?fetch chỉ tải về và cập nhật remote-tracking branch; pull là fetch rồi merge hoặc rebase.Làm việc với remote
  • ○ Nên biết Cấu hình và xác thực Git; vì sao .gitignore không có tác dụng với file đã commit?Ba cấp cấu hình system/global/local; .gitignore chỉ áp cho file chưa track — gỡ bằng git rm --cached; không để .env lọt vào repo.Cấu hình Git và xác thực.gitignore hoạt động thế nào
  • ○ Bắt buộc Chiến lược nhánh — trunk-based hay GitFlow?Nhánh ngắn 1–2 ngày, main luôn phát hành được; team release theo đợt thường thêm nhánh release/*.Chọn mô hình nhánh Git cho đội 5 người
  • ○ Bắt buộc Giải quyết merge conflict thế nào?Xem ba phía — gốc, của mình, của người kia — hiểu ý định từng bên rồi mới gộp; chạy test sau khi gộp.Xử lý merge conflict đúng cách
  • ○ Bắt buộc reset --soft/--mixed/--hard khác revert; khi nào được viết lại lịch sử?reset dời con trỏ nhánh; revert tạo commit đảo ngược — dùng cho nhánh đã chia sẻ.git reset --soft / --mixed / --hard ảnh hưởng vùng nào, khác git revert và git restore ra sao; commit --amend và git clean khi nào an toàn
  • ○ Nên biết Fast-forward, merge commit, squash, rebase merge?Fast-forward chỉ dịch con trỏ; three-way tạo merge commit; squash gộp cả nhánh thành một commit.Fast-forward vs three-way merge, --no-ff, và ba cách merge pull request (merge commit, squash, rebase)
  • ○ Nên biết Rebase và rebase -i để dọn commit trước khi mở PR?Phát lại commit lên điểm mới, mỗi commit có hash mới; không rebase nhánh người khác đang dùng.Rebase và interactive rebase
  • ○ Nên biết Commit message tốt, Conventional Commits, SemVer?Tiêu đề ngắn dạng mệnh lệnh, thân trả lời "vì sao"; loại commit quyết định tăng phiên bản nào.Commit message tốt và phát hành
  • ○ Nên biết PR tốt và bảo vệ nhánh?PR nhỏ, một mục đích; nhánh chính bắt buộc review, CI xanh, cấm force push.Pull request và bảo vệ nhánh
  • ○ Nâng cao Git hooks — pre-commit quét secret, commit-msg kiểm tra quy ước?Hook chạy ở máy dev, bỏ qua được; kiểm tra bắt buộc vẫn phải nằm ở CI.Git hooks

Docker

  • ○ Bắt buộc Image khác container; container khác máy ảo?Image là khuôn bất biến gồm các layer; container là process đang chạy từ image, dùng chung kernel với máy chủ.Docker image và container khác nhau thế nào? Container khác máy ảo ở điểm nào
  • ○ Bắt buộc ENTRYPOINT khác CMD; dạng exec khác dạng shell?ENTRYPOINT là chương trình luôn chạy, CMD là tham số mặc định; dạng exec để process nhận SIGTERM.ENTRYPOINT và CMD khác nhau thế nào
  • ○ Bắt buộc Viết Dockerfile tốt — multi-stage, thứ tự layer, non-root?Stage chạy chỉ có runtime và artifact; file ít đổi copy trước; USER không phải root; ghim phiên bản image nền.Viết Dockerfile production
  • ○ Bắt buộc Container thoát ngay hoặc không chạy — debug thế nào?docker ps -a xem exit code, docker logs, docker inspect, docker exec; exit 137 thường là bị kill vì hết bộ nhớ.Debug container bằng Docker CLI
  • ○ Nên biết Build trên CI chậm vì mất cache layer?Sắp layer đúng thứ tự, cache mount cho trình quản lý gói, cache từ registry cho runner mới.Build image nhanh trong CI
  • ○ Nên biết Vì sao ứng dụng trong container gọi localhost:5432 không tới database?localhost là chính container; gọi bằng tên service trong network của Compose; dữ liệu cần giữ nằm trong volume.Mạng và lưu trữ trong Docker Compose
  • ○ Nên biết Compose cho môi trường dev — healthcheck, depends_on?Ghim đúng phiên bản production; depends_on: condition: service_healthy thay vì sleep.Dùng Docker Compose cho môi trường phát triển cả đội
  • ○ Nên biết Tag khác digest; vì sao không dùng latest?Tag là nhãn di chuyển được, digest theo nội dung không đổi; latest không có nghĩa là mới nhất.Tag, digest và registry
  • ○ Nâng cao Bảo mật container — non-root, image tối giản, bỏ capability?Mục tiêu: nếu bị khai thác thì kẻ tấn công làm được ít nhất có thể.Bảo mật container

CI/CD

  • ○ Bắt buộc DevOps là gì — văn hoá hay công cụ?Cách làm việc để thay đổi đi nhanh và an toàn; CALMS; đo bằng DORA; "team DevOps" đứng giữa dễ thành silo.DevOps là gì
  • ○ Bắt buộc CI, Continuous Delivery, Continuous Deployment khác nhau; cache khác artifact?Delivery: luôn deploy được, bấm là lên; Deployment: tự lên production; cache để tăng tốc, artifact là sản phẩm.CI, Continuous Delivery, Continuous Deployment khác nhau thế nào; cấu trúc một workflow GitHub Actions (on, jobs, steps, needs, matrix, permissions, secrets), artifact vs cache, so với Jenkinsfile và GitLab CI
  • ○ Bắt buộc Mô tả pipeline CI/CD cho Angular + Spring Boot — build một lần, deploy nhiều nơi?CI trên mọi PR; CD đưa cùng một artifact qua các môi trường; đỏ ở đâu dừng ở đó.Mô tả một pipeline CI/CD cho Angular + Spring Boot
  • ○ Bắt buộc Đọc .gitlab-ci.yml: stages, needs, rules, biến protected, job manual?Biến protected chỉ có trên nhánh/tag được bảo vệ; job manual cần allow_failure: false mới chặn pipeline; resource_group chống deploy chồng.GitLab CI cho người mới vào team
  • ○ Bắt buộc Rolling, blue-green, canary — chọn gì cho hệ thanh toán?Rolling có hai phiên bản cùng chạy; blue-green chuyển toàn bộ, rollback nhanh; canary thử trên một phần traffic.Rolling, blue-green, canary và feature flag
  • ○ Nên biết Jenkinsfile declarative, shared library, credential?Pipeline as code trong repo; phần dùng chung đưa vào shared library; secret qua Credentials binding.Jenkins pipeline
  • ○ Nên biết Quy trình phát hành ở ngân hàng — DEV → SIT → UAT → production, CAB?Phiếu yêu cầu thay đổi, cửa sổ triển khai, đóng băng dịp Tết, kế hoạch rollback, tách nhiệm vụ.Quy trình phát hành ở ngân hàng
  • ○ Nên biết Build trong mạng ngân hàng không ra Internet?Kho artifact nội bộ (Nexus, Artifactory, Harbor) làm proxy; máy dev và CI chỉ nói chuyện với kho.Build trong mạng ngân hàng không ra Internet
  • ○ Nên biết Đo hiệu quả delivery bằng DORA?Tốc độ và độ ổn định đi cùng nhau; bộ hiện hành có 5 chỉ số.Chỉ số DORA
  • ○ Nâng cao CI chạy 45 phút — tăng tốc thế nào?Đo trước; chỉ build phần bị ảnh hưởng; cache; chạy song song.CI chạy 45 phút

Kubernetes

  • ○ Bắt buộc Kiến trúc Kubernetes — control plane và node?API server là cửa duy nhất; etcd lưu trạng thái; scheduler xếp pod; controller reconcile; kubelet chạy pod trên node.Kiến trúc Kubernetes
  • ○ Bắt buộc Pod, ReplicaSet, Deployment, Service?Pod dùng xong bỏ, IP thay đổi; Deployment quản lý cập nhật; Service cho tên và địa chỉ ổn định.Pod, ReplicaSet, Deployment, Service, Ingress/Gateway
  • ○ Bắt buộc ClusterIP, NodePort, LoadBalancer — service gọi nhau thế nào?Service chọn pod bằng label; ClusterIP cho gọi trong cụm; traffic ngoài vào qua LoadBalancer hoặc Gateway.Service trong Kubernetes
  • ○ Bắt buộc Debug một pod lỗi bằng kubectl?Kiểm tra đúng context và namespace trước; get → describe (events) → logs --previous → exec → port-forward.kubectl cho developer
  • ○ Bắt buộc Liveness, readiness, startup probe khác nhau thế nào?Readiness fail → rút khỏi Service; liveness fail → restart; liveness không kiểm tra database.Liveness, readiness, startup probe
  • ○ Bắt buộc ConfigMap và Secret; đổi cấu hình có cần restart pod?Biến môi trường chỉ đọc lúc khởi động, file mount được cập nhật; Secret chỉ là base64.ConfigMap và Secret
  • ○ Nên biết Deployment, StatefulSet, DaemonSet, Job — chọn gì?Stateless chạy liên tục → Deployment; cần danh tính và ổ riêng → StatefulSet; mỗi node một bản → DaemonSet.Deployment, StatefulSet, DaemonSet, Job, CronJob
  • ○ Nên biết Rolling update, maxSurge/maxUnavailable, HPA?Pod mới chỉ được tính khi readiness OK; HPA scale theo metric, cần requests đặt đúng.Rolling update, rollback và HPA
  • ○ Nên biết Ingress và Gateway API?ingress-nginx đã ngừng phát triển từ 3/2026; Gateway API tách vai trò hạ tầng và ứng dụng.Ingress và Gateway API

Tình huống sự cố

Trả lời theo khung 5 bước: làm rõ (ảnh hưởng ai, từ lúc nào, vừa thay đổi gì) → giảm thiệt hại (rollback, chuyển traffic) → tìm nguyên nhân bằng dữ liệu (lệnh nào, thấy gì) → sửa gốc → phòng ngừa (cảnh báo, test, runbook). Ở level Junior, người phỏng vấn chấm nhiều nhất ở bước 3: bạn có nói ra lệnh cụ thể không.

  • ○ Bắt buộc "Máy tôi chạy được, staging thì không"?Liệt kê khác biệt giữa hai môi trường rồi loại trừ từng cái, bắt đầu từ lỗi thật trên staging.Tình huống: chạy trên máy tôi thì được, lên staging thì lỗi
  • ○ Bắt buộc Pod CrashLoopBackOff sau khi deploy?Xem ảnh hưởng trước; logs --previous, describe xem exit code và events; rollback nếu người dùng bị ảnh hưởng.Tình huống: deploy xong pod CrashLoopBackOff
  • ○ Bắt buộc ImagePullBackOff?Đọc thông điệp trong describe: tag không tồn tại, không có quyền pull, hay không tới được registry.Tình huống: pod mới kẹt ImagePullBackOff khi scale
  • ○ Bắt buộc Pod Pending mãi?FailedScheduling ghi rõ lý do: thiếu CPU/bộ nhớ, taint, affinity, PVC chưa bind.Tình huống: pod mới nằm Pending mãi trong lúc scale ngày cao điểm
  • ○ Nên biết Deploy xong, pod Running nhưng gateway trả 503?Đi theo đường request: route → Service → endpoint → readiness → cổng của container.Tình huống: pipeline báo deploy thành công, pod Running, nhưng người dùng nhận 503
  • ○ Nên biết Gọi API đối tác lỗi TLS — nghi chứng chỉ hết hạn?Xác định chứng chỉ nào hết hạn bằng openssl s_client từ chính pod; cách sửa khác nhau theo từng loại.Tình huống: nửa đêm mọi lời gọi tới API đối tác lỗi 'certificate expired'
  • ○ Nên biết Disk của database đầy?Không xoá file trong thư mục dữ liệu bằng tay, nhất là WAL; mở rộng volume trước, tìm nguyên nhân sau.Tình huống: database (hoặc node Kubernetes) đầy đĩa, ghi lỗi
  • ○ Nên biết CI lúc xanh lúc đỏ?Đo tỷ lệ test chập chờn, cách ly test đó, sửa nguyên nhân; đừng để mọi người quen merge khi đỏ.Tình huống: CI đỏ ngẫu nhiên khoảng 1/5 lần, team quen bấm re-run
  • ○ Nên biết Lỡ commit 3 commit vào main?Chưa push thì dời con trỏ; đã push thì không viết lại lịch sử chung — dùng revert.Tình huống: lỡ commit thẳng lên main (chưa push / đã push), commit nhầm nhánh, đang sửa dở trên nhầm nhánh
