SQL từ con số 0 cho dev Frontend

Lộ trình 26 tuần (8–10 giờ/tuần) từ chưa biết database tới SQL chuyên sâu cho backend Java ở ngân hàng, bảo hiểm — 9 giai đoạn, mỗi giai đoạn có thứ tự học và lý do, chỗ dễ nhầm so với Frontend, khác biệt PostgreSQL/MySQL/Oracle/SQL Server, nguồn học, bài tập, dự án và tiêu chí qua cửa.

Trang này dành cho người đã làm Frontend (Angular/TypeScript) vài năm nhưng chưa từng làm việc với SQL, muốn đi tới mức viết SQL đúng và nhanh, thiết kế được schema, hiểu transaction và khoá, và dùng được JPA mà không bị nó "lừa" — đủ để làm backend Java Spring Boot ở ngân hàng, bảo hiểm và qua phỏng vấn.

Đối chiếu ngày 12/11/2026: ví dụ chạy trên PostgreSQL 18 (bản ổn định mới nhất; nhiều ngân hàng còn chạy 13–16 hoặc Oracle). MySQL dùng 8.4 LTS trở lên (8.0 hết hỗ trợ từ 4/2026). Chỗ nào PostgreSQL khác MySQL, Oracle, SQL Server đủ để gây lỗi, mỗi giai đoạn có mục Khác biệt giữa các DBMS.

Tài liệu học theo level — học cái nào trước, đọc phần nào, bài tập ở đâu: Tài liệu SQL theo level. Mục Nguồn học trong từng giai đoạn bên dưới có link bấm được.

Bộ câu hỏi phỏng vấn đi kèm lộ trình này chia theo level: Newbie · Junior · Middle · Senior. Trang Checklist Data & SQL chuyên sâu là bản tra cứu theo chủ đề cho người đã có nền.

Cách dùng trang này

  • Đi đúng thứ tự giai đoạn. Mỗi giai đoạn dùng kiến thức của giai đoạn trước; nhảy cóc sang index hay JPA khi chưa vững JOIN và NULL là cách nhanh nhất để học vẹt.
  • Chỉ sang giai đoạn sau khi đạt "Qua cửa", không phải khi đọc hết. Tiêu chí qua cửa là việc làm được và đo được.
  • Mỗi tuần 9 giờ: 2 giờ đọc/xem → 5 giờ tự gõ bài tập → 1,5 giờ dự án → 0,5 giờ ghi "sổ lỗi" (câu sai, vì sao sai, cách nhớ). Gõ trong psql ít nhất một nửa thời gian — vòng live coding thường không có autocomplete.
  • Mục "Đọc sâu trong app" ở cuối mỗi giai đoạn là các câu trong ngân hàng câu hỏi: mở ra, tự trả lời thành tiếng trước rồi mới xem đáp án, chấm điểm để app nhắc ôn lại.
  • Một dự án xuyên suốt: mini-bank. Bắt đầu từ 2 bảng ở giai đoạn 1, lớn dần thành sổ cái kép có hàng triệu giao dịch, chịu tải đồng thời, có API Spring Boot ở giai đoạn 7 và sẵn sàng vận hành ở giai đoạn 8. Cuối lộ trình bạn có một repo để kể trong phỏng vấn thay vì 50 bài tập rời rạc.

Ký hiệu nguồn học: ✅ chắc chắn có thật và miễn phí · 💰 trả phí · ⚠️ có thật nhưng nội dung, đường dẫn hoặc tên có thể đã đổi — tìm theo tên.

Tổng khoảng 26 tuần (~6 tháng), ~230 giờ. Nếu chỉ được 8 giờ/tuần, cộng thêm khoảng 3 tuần. Học xong bạn có kiến thức vững cho phỏng vấn Junior và Middle; Senior thật cần thêm trải nghiệm production (sự cố, migration trên bảng lớn, trực đêm) — lộ trình cho bạn đủ điều kiện cần và câu chuyện để kể.

Một thay đổi so với thứ tự thường thấy: SQL trong Java (giai đoạn 7) đứng trước Vận hành (giai đoạn 8). JPA, @Transactional, N+1 là thứ bạn dùng hằng ngày và bị hỏi ở mọi vòng Java backend; backup, replication chủ yếu là việc của DBA/DevOps và hay hỏi ở mức Senior. Flyway cũng học tự nhiên nhất khi đã có project Spring Boot.

Ba thay đổi tư duy lớn nhất khi từ Frontend sang

  1. Nghĩ theo tập hợp, không theo vòng lặp. Bạn mô tả kết quả muốn có, database tự chọn cách lấy (bộ phận đó gọi là query planner). Viết vòng for gọi database cho từng dòng chậm đúng như gọi API trong @for.
  2. Dữ liệu sống lâu hơn code. Sửa component thì deploy lại là xong; schema sai thì phải migrate hàng trăm triệu dòng đang chạy, trong lúc người dùng vẫn giao dịch.
  3. Đồng thời là mặc định. Ở Frontend, state thuộc một người trong một tab. Ở database, 1.000 request có thể sửa cùng một tài khoản cùng lúc. Phần lớn bug mất tiền ở ngân hàng nằm ở đây.

Giai đoạn 1 — Nền tảng (tuần 1–2)

Mục tiêu: tự dựng database, tạo bảng có ràng buộc, đọc và sửa dữ liệu mà không làm hỏng gì.

Chủ đề theo thứ tự

  1. Khái niệm cốt lõi.
    • Database: tập dữ liệu có tổ chức. DBMS: phần mềm quản lý nó (PostgreSQL, Oracle, MySQL, SQL Server).
    • Relational database (cơ sở dữ liệu quan hệ): dữ liệu nằm trong table (bảng) gồm row (dòng — một bản ghi) và column (cột — một thuộc tính có kiểu cố định); các bảng liên kết với nhau qua key (khoá).
    • SQL: ngôn ngữ khai báo — nói muốn gì, không nói làm thế nào. Bốn nhóm lệnh: DDL định nghĩa cấu trúc (CREATE, ALTER, DROP), DML thao tác dữ liệu (SELECT, INSERT, UPDATE, DELETE), DCL phân quyền (GRANT, REVOKE), TCL quản lý transaction (BEGIN, COMMIT, ROLLBACK).
    • Transaction: nhóm lệnh hoặc thành công tất cả, hoặc không lệnh nào có hiệu lực. Ở giai đoạn này chỉ cần dùng nó như nút Undo; giai đoạn 6 mới học kỹ.
    • Mô hình client–server: ứng dụng (hoặc psql/DBeaver) mở connection tới server PostgreSQL, gửi câu SQL, nhận kết quả.
  2. Cài đặt và công cụ: Docker, psql, DBeaver/pgAdmin (mục Môi trường học ở trên).
  3. Cấp tổ chức: cluster (một server) → database → schema (namespace chứa bảng, mặc định public) → table.
  4. Kiểu dữ liệu hay dùng: bigint, integer, numeric(p,s) (số chính xác — dùng cho tiền), text, varchar(n), boolean, date, timestamptz, uuid; jsonb chỉ cần biết là có.
  5. CREATE TABLE và constraint — quy tắc dữ liệu database tự kiểm tra mỗi lần ghi: PRIMARY KEY (khoá chính — định danh duy nhất mỗi dòng), FOREIGN KEY ... REFERENCES (khoá ngoại — trỏ sang bảng khác, kèm ON DELETE RESTRICT | CASCADE | SET NULL), NOT NULL, UNIQUE, CHECK, DEFAULT; identity column (cột số tự tăng do database sinh); ALTER TABLE cơ bản.
  6. INSERT: chèn nhiều dòng một lần; RETURNING trả lại dòng vừa ghi — giống API POST trả về object vừa tạo.
  7. SELECT: WHERE (=, <>, AND/OR, IN, BETWEEN, LIKE/ILIKE), ORDER BY, LIMIT/OFFSET, DISTINCT, alias.
  8. NULL: logic ba giá trị (TRUE / FALSE / UNKNOWN), IS NULL, COALESCE, IS DISTINCT FROM.
  9. UPDATE, DELETE, TRUNCATE cùng thói quen bọc trong transaction.

Vì sao thứ tự này: có môi trường chạy trước → biết cấu trúc (DDL) để hiểu dữ liệu nằm ở đâu → đưa dữ liệu vào → đọc ra → NULL ngay sau SELECT vì WHERE sai với NULL là bug số một của người mới → UPDATE/DELETE học cuối cùng, vì chúng dùng chung WHERE, và ở đây viết sai WHERE là mất dữ liệu thật.

-- Thói quen bắt buộc khi sửa hoặc xoá: transaction làm nút Undo
BEGIN;
UPDATE accounts SET status = 'LOCKED' WHERE customer_id = 3;
SELECT id, status FROM accounts WHERE customer_id = 3;  -- kiểm tra kết quả
ROLLBACK;                                               -- sai thì hoàn tác; đúng thì COMMIT

Khác biệt giữa các DBMS

  • Cột tự tăng: PostgreSQL GENERATED ALWAYS AS IDENTITY (SERIAL là cách cũ); MySQL AUTO_INCREMENT; Oracle 12c+ có identity (code cũ dùng SEQUENCE + trigger); SQL Server IDENTITY(1,1).
  • Chuỗi rỗng: Oracle coi '' là NULL — bẫy lớn khi chuyển code giữa Oracle và PostgreSQL.
  • Giới hạn số dòng: PostgreSQL, MySQL dùng LIMIT; chuẩn SQL và Oracle 12c+ dùng FETCH FIRST n ROWS ONLY (PostgreSQL cũng hiểu); code Oracle cũ dùng ROWNUM; SQL Server dùng TOP n hoặc OFFSET … FETCH.
  • Boolean: Oracle chỉ có kiểu cột BOOLEAN từ 23ai; code cũ dùng NUMBER(1) hoặc CHAR(1).
  • So sánh chuỗi: collation mặc định của MySQL không phân biệt hoa thường; PostgreSQL thì phân biệt (dùng ILIKE hoặc lower()).
  • NULL khi ORDER BY ... ASC: PostgreSQL, Oracle đặt NULL cuối; MySQL, SQL Server đặt NULL đầu.
  • DDL trong transaction: PostgreSQL ROLLBACK được cả CREATE/ALTER/DROP; MySQL và Oracle tự commit khi gặp DDL — rất quan trọng khi học migration ở giai đoạn 8.

Bài tập

Schema đầu tiên của mini-bank:

-- sql/01_schema.sql — mini-bank v0
DROP TABLE IF EXISTS accounts, customers CASCADE;

CREATE TABLE customers (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  full_name  text        NOT NULL,
  email      text        NOT NULL UNIQUE,
  phone      text,                                   -- được phép NULL
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE accounts (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint        NOT NULL REFERENCES customers(id),
  account_no  varchar(20)   NOT NULL UNIQUE,
  currency    text          NOT NULL DEFAULT 'VND' CHECK (currency ~ '^[A-Z]{3}$'),
  balance     numeric(19,2) NOT NULL DEFAULT 0 CHECK (balance >= 0),
  status      text          NOT NULL DEFAULT 'ACTIVE'
              CHECK (status IN ('ACTIVE', 'LOCKED', 'CLOSED'))
);
  1. Dựng Docker, kết nối bằng cả psql và DBeaver, chạy SELECT version();.
  2. Chạy schema trên. Insert 6 khách hàng (2 người không có số điện thoại) và 10 tài khoản. Rồi cố tình gây lỗi và đọc kỹ thông báo: insert tài khoản với customer_id = 999; balance = -1; status = 'FROZEN'; email trùng; xoá một khách đang có tài khoản.
  3. Bài NULL — đoán kết quả trước khi chạy:
    SELECT NULL = NULL, NULL IS NULL, 7 / 2, 7 / 2.0;
SELECT 1 WHERE 3 NOT IN (1, 2, NULL);                   -- vì sao 0 dòng?
SELECT count(*), count(phone) FROM customers;
SELECT full_name, phone FROM customers ORDER BY phone;  -- NULL nằm ở đâu?
  4. Hết pgexercises Simple SQL Queries và Modifying data.
  5. Viết 10 câu UPDATE/DELETE, câu nào cũng theo khuôn BEGIN → lệnh → SELECT kiểm tra → ROLLBACK/COMMIT.

Chủ đề theo thứ tự

  1. Thứ tự thực thi logic. SQL được viết theo một thứ tự nhưng được hiểu theo thứ tự khác:
    FROM / JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
    Hệ quả: alias đặt trong SELECT chưa tồn tại lúc WHERE chạy (PostgreSQL cho dùng alias ở ORDER BY, không cho ở WHERE).
  2. JOIN — ghép dòng của hai bảng theo điều kiện ON: INNER JOIN (chỉ giữ cặp khớp), LEFT JOIN (giữ mọi dòng bên trái, chỗ không khớp điền NULL), RIGHT JOIN (ít dùng — đảo bảng thành LEFT), FULL OUTER JOIN, CROSS JOIN (mọi tổ hợp), self-join (bảng JOIN với chính nó); JOIN 3–5 bảng; điều kiện trong ON khác điều kiện trong WHERE thế nào.
  3. Hàm tổng hợp (aggregate — gộp nhiều dòng thành một giá trị): COUNT(*), COUNT(col), COUNT(DISTINCT col), SUM, AVG, MIN, MAX; GROUP BY; HAVING; FILTER (WHERE …) của PostgreSQL.
  4. Subquery (câu SELECT lồng trong câu khác): scalar (trả một giá trị), với IN, EXISTS, NOT EXISTS, correlated (tham chiếu dòng của câu ngoài — chạy theo từng dòng), derived table (subquery trong FROM).
  5. Phép toán tập hợp: UNION, UNION ALL, INTERSECT, EXCEPT.
  6. Ép kiểu (::numeric, CAST), hàm chuỗi và số cơ bản.

Vì sao thứ tự này: thứ tự thực thi là "bản đồ" giải thích hầu hết lỗi về sau → JOIN trước aggregate vì thực tế hay tổng hợp trên dữ liệu đã JOIN, và lỗi nhân dòng (fan-out) chỉ hiểu được khi đã nắm JOIN → subquery lồng hai thứ trên → phép tập hợp ít dùng hơn nên để cuối.

Lời khuyên: đừng hiểu JOIN bằng biểu đồ Venn. Hãy hình dung xét mọi cặp dòng (trái, phải), giữ cặp thoả ON — cách nhìn này giải thích ngay vì sao số dòng bị nhân lên.

-- ❌ LEFT JOIN vô tình thành INNER JOIN
SELECT c.full_name, a.account_no
FROM customers c
LEFT JOIN accounts a ON a.customer_id = c.id
WHERE a.status = 'ACTIVE';     -- khách chưa có tài khoản (a.* là NULL) bị loại

-- ✅ điều kiện của bảng bên phải đặt trong ON
SELECT c.full_name, a.account_no
FROM customers c
LEFT JOIN accounts a ON a.customer_id = c.id AND a.status = 'ACTIVE';

CREATE TABLE transactions (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  account_id bigint        NOT NULL REFERENCES accounts(id),
  amount     numeric(19,2) NOT NULL CHECK (amount <> 0),  -- dương: tiền vào, âm: tiền ra
  txn_type   text          NOT NULL,
  created_at timestamptz   NOT NULL DEFAULT now()
);

Viết: số dư mỗi tài khoản tính từ giao dịch; khách không có tài khoản nào; tài khoản có tổng tiền ra trong tháng vượt 50 triệu.

Chủ đề theo thứ tự

  1. CASE và tổng hợp có điều kiện (SUM(CASE …) hoặc FILTER) để xoay bảng (pivot).
  2. CTE (Common Table Expression — WITH ten AS (...)): đặt tên cho kết quả trung gian để câu dài dễ đọc.
  3. CTE đệ quy (WITH RECURSIVE): duyệt dữ liệu dạng cây — sơ đồ tổ chức, hệ thống tài khoản kế toán, danh mục nhiều cấp.
  4. Window function — hàm tính trên một "cửa sổ" các dòng liên quan mà không gộp dòng: OVER (PARTITION BY … ORDER BY … [frame]) (frame là phạm vi dòng mà hàm nhìn thấy); xếp hạng ROW_NUMBER, RANK, DENSE_RANK; LAG, LEAD; luỹ kế SUM() OVER; trung bình trượt; FIRST_VALUE, LAST_VALUE; NTILE.
  5. Ngày giờ: date, timestamp vs timestamptz, interval, date_trunc, extract, generate_series, AT TIME ZONE 'Asia/Ho_Chi_Minh'; lọc theo nửa khoảng >= đầu AND < cuối.
  6. JSON: json vs jsonb, toán tử ->, ->>, @>, jsonb_build_object, jsonb_agg; JSON_TABLE (PostgreSQL 17+).
  7. Upsert (chèn nếu chưa có, cập nhật nếu đã có): INSERT … ON CONFLICT DO NOTHING / DO UPDATE, và MERGE (PostgreSQL 15+).
  8. Đặc sản PostgreSQL: DISTINCT ON (dòng đầu tiên mỗi nhóm), RETURNING.
  9. Mẫu bài toán kinh điển: top-N mỗi nhóm, lương cao thứ N, khử trùng giữ bản mới nhất, số dư luỹ kế, gaps & islands (chuỗi ngày liên tiếp), tăng trưởng so tháng trước, pivot, tìm ngày/id bị thiếu, median (percentile_cont).

Vì sao thứ tự này: CASE dùng ở mọi phần sau → CTE trước window vì bài window thường cần chia bước → window là phần bị hỏi nhiều nhất khi live coding → ngày giờ và JSON là kiểu dữ liệu đặc thù → upsert gắn với ghi dữ liệu thật (import file, đồng bộ) → các mẫu bài toán để cuối vì kết hợp tất cả.

-- GROUP BY gộp: mỗi tài khoản còn 1 dòng
SELECT account_id, sum(amount) FROM transactions GROUP BY account_id;

-- Window giữ nguyên từng giao dịch, thêm cột số dư luỹ kế
SELECT account_id, created_at, amount,
       sum(amount) OVER (PARTITION BY account_id
                         ORDER BY created_at, id
                         ROWS UNBOUNDED PRECEDING) AS running_balance
FROM transactions;

  6. Khử trùng: bảng statement_import có dòng trùng theo (account_no, bank_ref) — giữ bản imported_at mới nhất, xoá phần còn lại.
  7. Upsert: bảng tỷ giá (currency, rate_date) — import lại file cùng ngày thì cập nhật; viết bằng ON CONFLICT, rồi bằng MERGE.
  8. JSON: cột payload jsonb giả lập response từ core banking — lọc payload @> '{"channel":"MOBILE"}', trích trường lồng nhau, và trả kết quả đúng shape JSON mà FE cần bằng jsonb_agg + jsonb_build_object.

Dự án nhỏ — mini-bank v0.5 (báo cáo): số dư cuối ngày từng tài khoản trong 30 ngày; top 5 khách giao dịch nhiều nhất mỗi tháng; cảnh báo giao dịch lớn hơn 3 lần trung bình 30 ngày trước đó của chính tài khoản:

avg(amount) OVER (PARTITION BY account_id ORDER BY created_at
                  RANGE BETWEEN INTERVAL '30 days' PRECEDING AND CURRENT ROW
                  EXCLUDE CURRENT ROW)

và một API sao kê trả JSON. Đề chi tiết: Dự án: mini-bank v0.5 — thêm bảng giao dịch, sinh 200.000 dòng giả lập, viết 12 báo cáo nghiệp vụ, mỗi báo cáo hai cách và chứng minh cùng kết quả bằng EXCEPT ALL.

Giai đoạn 4 — Thiết kế dữ liệu (tuần 9–11)

Mục tiêu: từ một mô tả nghiệp vụ, vẽ ERD, ra bảng có ràng buộc, và bảo vệ được từng quyết định (khoá, kiểu tiền, xoá mềm, audit).

Chủ đề theo thứ tự

  1. Quy trình: yêu cầu nghiệp vụ → entity (thực thể, ví dụ Khách hàng) → attribute (thuộc tính) → quan hệ → ERD (sơ đồ thực thể–quan hệ, ký hiệu crow's foot) — đi từ mức khái niệm → logic → vật lý.
  2. Quan hệ 1-1, 1-n, n-n (bảng trung gian); quan hệ có thuộc tính riêng (tài khoản đồng sở hữu: account_holders(account_id, customer_id, role)).
  3. Khoá: natural key (khoá có nghĩa nghiệp vụ — số CCCD) vs surrogate key (id vô nghĩa do database sinh); bigint identity vs UUID (UUID v4 ngẫu nhiên làm index phân mảnh; UUID v7 sắp theo thời gian, PostgreSQL 18 có uuidv7()).
  4. Chuẩn hoá (normalization — tách bảng để mỗi sự thật chỉ lưu một chỗ): anomaly (bất thường khi thêm/sửa/xoá) → functional dependency (cột A xác định duy nhất cột B) → 1NF → 2NF → 3NF → BCNF, mỗi dạng một ví dụ.
  5. Phi chuẩn hoá có chủ đích: lưu sẵn số dư cạnh sổ cái, cột tổng hợp, materialized view. Phân biệt: giá hoặc tỷ giá tại thời điểm giao dịch không phải dư thừa — đó là một sự thật khác cần lưu.
  6. Nghiệp vụ thực tế: ngân hàng — khách hàng, tài khoản, chủ tài khoản, sổ cái bút toán kép (double-entry ledger: mỗi giao dịch có ≥ 2 bút toán, tổng nợ bằng tổng có), idempotency key (chống xử lý trùng khi client gửi lại), lịch sử trạng thái; bảo hiểm — hợp đồng, người được bảo hiểm, phí theo kỳ, hồ sơ bồi thường.
  7. Lưu tiền: numeric(19,4) hoặc bigint theo đơn vị nhỏ nhất (VND có 0 chữ số thập phân theo ISO 4217); luôn kèm mã tiền tệ; quy tắc làm tròn và phân bổ phần dư; không float, không kiểu money của PostgreSQL.
  8. Soft delete (deleted_at thay vì xoá thật) và trade-off: UNIQUE phải thành partial index, query nào cũng phải lọc, xung đột với nghĩa vụ xoá dữ liệu cá nhân; thay thế bằng bảng archive.
  9. Audit log: ai, khi nào, sửa gì, giá trị trước–sau; ba cách làm — trigger, tầng ứng dụng (Hibernate Envers), CDC; chỉ thêm, không sửa, không xoá (append-only).
  10. Quy ước đặt tên, created_at/updated_at; enum bằng CHECK, bảng lookup hay kiểu ENUM.

Vì sao học sau SQL nâng cao: một schema chỉ đánh giá được qua câu hỏi "query trên nó có dễ viết và đúng không" — phải viết được query trước mới thấy thiết kế tệ. Trong giai đoạn: ERD là ngôn ngữ chung → chuẩn hoá để "khám sức khoẻ" ERD → phi chuẩn hoá chỉ sau khi hiểu luật → nghiệp vụ thực tế để áp dụng tất cả.

-- Sổ cái bút toán kép (mini-bank v1)
CREATE TABLE journal_entries (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  idempotency_key uuid NOT NULL UNIQUE,   -- client gửi lại cùng request thì không ghi 2 lần
  entry_type      text NOT NULL,          -- TRANSFER, FEE, INTEREST...
  created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE postings (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  entry_id   bigint NOT NULL REFERENCES journal_entries(id),
  account_id bigint NOT NULL REFERENCES accounts(id),
  amount     numeric(19,4) NOT NULL CHECK (amount <> 0)  -- âm = nợ, dương = có (quy ước của bạn)
);

-- Bất biến: mỗi bút toán phải cân — câu này luôn phải trả rỗng
SELECT entry_id FROM postings GROUP BY entry_id HAVING sum(amount) <> 0;

Khác biệt giữa các DBMS

  • Kiểu cho tiền: Oracle NUMBER(19,4), MySQL/SQL Server DECIMAL(19,4); kiểu MONEY của SQL Server ít được khuyên dùng.
  • Lịch sử thay đổi tự động: SQL Server có system-versioned temporal table, Oracle có Flashback Data Archive; PostgreSQL chưa có sẵn — làm bằng trigger hoặc extension.

  • Chuỗi rỗng: vì Oracle coi '' là NULL, cột chuỗi NOT NULL trên Oracle cũng từ chối chuỗi rỗng.

Giai đoạn 5 — Hiệu năng (tuần 12–14)

Mục tiêu: đọc được kế hoạch thực thi, thiết kế index theo truy vấn, sửa query chậm và chứng minh bằng số đo.

Chủ đề theo thứ tự

  1. Database lưu dữ liệu thế nào: dữ liệu nằm trong các page 8 KB; bảng PostgreSQL là heap (các dòng không sắp xếp); đọc từ đĩa vs từ bộ nhớ đệm (shared_buffers). Vì vậy "số page phải đọc" là thước đo thật của chi phí.
  2. EXPLAIN và EXPLAIN (ANALYZE, BUFFERS): đọc cây plan từ trong ra ngoài; cost, rows ước lượng vs actual rows, loops, buffers hit/read. ANALYZE chạy thật câu lệnh — với UPDATE/DELETE phải bọc trong BEGIN … ROLLBACK.
  3. Seq Scan vs Index Scan vs Bitmap Scan; B-tree hoạt động thế nào (cây cân bằng, tìm trong O(log n), lá nối nhau nên quét khoảng được); selectivity (tỉ lệ dòng được chọn).
  4. Các loại index: B-tree (mặc định); composite và thứ tự cột (bằng trước, khoảng sau; quy tắc tiền tố trái — PostgreSQL 18 có skip scan nhưng chỉ hiệu quả khi cột đầu ít giá trị); covering (INCLUDE, index-only scan và visibility map); partial (WHERE status = 'PENDING'); expression (lower(email)); unique index; GIN (jsonb, full-text, trigram), BRIN (dữ liệu chỉ thêm theo thời gian).
  5. Điều kiện "giết" index (sargability): hàm trên cột, ép kiểu ngầm, LIKE '%x', OR trên nhiều cột, so sánh khác kiểu — và cách viết lại.
  6. Thuật toán JOIN: Nested Loop, Hash Join, Merge Join — khi nào planner chọn cái nào.
  7. Thống kê: ANALYZE, pg_stats, ước lượng sai → plan sai; CREATE STATISTICS cho các cột tương quan.
  8. Phân trang: OFFSET lớn chậm vì vẫn phải đọc rồi bỏ → keyset (WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20).
  9. VACUUM đủ dùng: mỗi UPDATE tạo phiên bản dòng mới, phiên bản cũ thành dead tuple; autovacuum dọn; bloat (phình bảng); VACUUM FULL khoá cả bảng. Vì sao lại như vậy (MVCC) học ở giai đoạn 6.
  10. Tìm query chậm trong production: pg_stat_statements, log_min_duration_statement, auto_explain.
  11. Cái giá của index: mỗi INSERT/UPDATE phải cập nhật mọi index liên quan, tốn dung lượng; tìm index không ai dùng (pg_stat_user_indexes.idx_scan = 0).

Vì sao thứ tự này: hiểu cách lưu trước, nếu không index là phép màu → học EXPLAIN (công cụ đo, như tab Performance của DevTools) trước các loại index để index nào học cũng đo được → loại index → điều kiện làm hỏng index → JOIN → thống kê (lý do plan đổi) → phân trang → vacuum → cuối cùng là tìm query chậm từ góc nhìn production.

Giai đoạn 6 — Transaction và đồng thời (tuần 15–17)

Mục tiêu: hiểu và tái hiện được các lỗi đồng thời, chọn đúng cách chặn từng lỗi, viết chuyển tiền đúng khi 50 phiên chạy cùng lúc.

Chủ đề theo thứ tự

  1. Transaction và ACID bằng ví dụ chuyển tiền: Atomicity (cả hai bút toán hoặc không gì), Consistency (ràng buộc luôn đúng), Isolation (các transaction không thấy trạng thái dở dang của nhau — ở mức nào), Durability (đã commit thì không mất khi sập). BEGIN/COMMIT/ROLLBACK/SAVEPOINT; autocommit; ở PostgreSQL, một lỗi trong transaction làm cả transaction aborted — phải ROLLBACK (hoặc quay về SAVEPOINT).
  2. Bất thường đồng thời (anomaly), mỗi cái một ví dụ ngân hàng: dirty read (đọc dữ liệu chưa commit), non-repeatable read (đọc lại một dòng thấy khác), phantom read (đọc lại một tập thấy thêm/bớt dòng), lost update (hai bên đọc–sửa–ghi, một bên ghi đè bên kia), read skew, write skew (hai transaction đọc chung một điều kiện, mỗi bên ghi chỗ khác, cùng nhau phá điều kiện).
  3. Isolation level và cách PostgreSQL hiện thực: READ COMMITTED (mặc định — mỗi câu lệnh một snapshot), REPEATABLE READ (một snapshot cho cả transaction; cập nhật dòng đã bị người khác sửa thì lỗi), SERIALIZABLE (SSI — có thể lỗi 40001, bắt buộc retry).
  4. MVCC (Multi-Version Concurrency Control): mỗi dòng có nhiều phiên bản (xmin/xmax), UPDATE tạo phiên bản mới, đọc không chặn ghi, ghi không chặn đọc; transaction mở lâu giữ phiên bản cũ → bloat (nối với VACUUM ở giai đoạn 5).
  5. Khoá dòng: SELECT … FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE; NOWAIT; SKIP LOCKED (hàng đợi job); lock_timeout.
  6. Cập nhật nguyên tử — cách đơn giản nhất chống lost update: UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100, rồi kiểm tra số dòng bị ảnh hưởng.
  7. Optimistic (cột version, kiểm tra khi ghi) vs pessimistic (FOR UPDATE, khoá khi đọc) — chọn theo mức xung đột và chi phí làm lại.
  8. Deadlock: hai transaction chờ khoá của nhau; PostgreSQL phát hiện (sau deadlock_timeout, mặc định 1 giây) và huỷ một bên; phòng bằng thứ tự khoá nhất quán (khoá tài khoản id nhỏ trước) và transaction ngắn.
  9. Khoá bảng và DDL: ALTER TABLE lấy khoá ACCESS EXCLUSIVE, chặn cả SELECT; lock queue — một ALTER đang chờ sẽ chặn mọi câu đến sau nó (nối sang migration ở giai đoạn 8).
  10. Advisory lock (pg_advisory_xact_lock): khoá theo khoá nghiệp vụ không gắn với dòng nào.
  11. Idempotency và retry: idempotency key UNIQUE + INSERT … ON CONFLICT; retry có giới hạn khi gặp 40001 (serialization failure) và 40P01 (deadlock).

Vì sao thứ tự này: ACID trước → bất thường (vấn đề) trước isolation level (lời giải), vì mỗi level được định nghĩa bằng việc nó chặn bất thường nào → MVCC giải thích PostgreSQL làm điều đó thế nào → khoá cho những chỗ isolation không tự giải quyết → optimistic/pessimistic là lựa chọn thiết kế → deadlock sinh ra từ khoá → idempotency và retry cho thực tế mạng chập chờn.

Khác biệt giữa các DBMS

  • Mặc định: PostgreSQL, Oracle, SQL Server là READ COMMITTED; MySQL InnoDB là REPEATABLE READ.
  • PostgreSQL không có dirty read ở mọi mức (READ UNCOMMITTED chạy như READ COMMITTED), và REPEATABLE READ của PostgreSQL chặn cả phantom. Muốn thấy dirty read phải dùng SQL Server (NOLOCK / READ UNCOMMITTED) hoặc MySQL.
  • Oracle chỉ có READ COMMITTED và SERIALIZABLE — SERIALIZABLE của Oracle thực chất là snapshot isolation, không chặn write skew như PostgreSQL.
  • MySQL REPEATABLE READ dùng gap lock/next-key lock khi đọc có khoá → kiểu deadlock khác PostgreSQL.
  • SQL Server mặc định (khi chưa bật READ_COMMITTED_SNAPSHOT) dùng khoá đọc: người đọc có thể chặn người ghi.
  • Lỗi giữa transaction: PostgreSQL làm cả transaction aborted; Oracle, MySQL chỉ rollback câu lệnh lỗi — code Java chuyển từ Oracle sang PostgreSQL hay vấp chỗ này.

  7. Lock queue: phiên A mở transaction đọc bảng (chưa commit); phiên B chạy ALTER TABLE … ADD COLUMN → chờ; phiên C chạy SELECT → cũng bị chặn. Sửa: SET lock_timeout = '3s' + retry.

Giai đoạn 7 — SQL trong Java: JDBC, JPA, Spring (tuần 18–20)

Chủ đề theo thứ tự

  7. LazyInitializationException và Open Session in View (spring.jpa.open-in-view mặc định bật kèm cảnh báo) — vì sao nên tắt.
  8. @Transactional: chạy qua proxy (gọi nội bộ this.method() không có transaction); mặc định chỉ rollback với unchecked exception; readOnly; propagation REQUIRED/REQUIRES_NEW; isolation; đặt ranh giới ở tầng service; không gọi HTTP bên trong.

Giai đoạn 8 — Vận hành (tuần 21–22)

Mục tiêu: thay đổi schema trên bảng lớn mà không làm treo hệ thống, khôi phục được dữ liệu về một thời điểm, và phân quyền theo nguyên tắc tối thiểu.

Chủ đề theo thứ tự

  1. Migration: Flyway (versioned V1__…, repeatable R__…, bảng flyway_schema_history, checksum — không sửa migration đã chạy) và Liquibase (changelog, changeset, bảng DATABASECHANGELOG, rollback); chạy migration lúc ứng dụng khởi động hay bằng job riêng trong CI/CD.
  2. Đổi schema an toàn trên bảng lớn: khoá và lock_timeout; ADD COLUMN có DEFAULT hằng số không ghi lại bảng (PostgreSQL 11+); thêm NOT NULL qua CHECK … NOT VALID rồi VALIDATE; CREATE INDEX CONCURRENTLY (không chạy được trong transaction); expand/contract (đổi tên cột qua nhiều lần deploy); backfill theo lô.
  3. Backup/restore: logic (pg_dump/pg_restore, định dạng -Fc) vs vật lý (pg_basebackup) + lưu trữ WAL liên tục → PITR (khôi phục về một thời điểm); công cụ pgBackRest, Barman; RPO/RTO. Backup chưa restore thử thì coi như chưa có.
  4. Replication: streaming (vật lý) đồng bộ/bất đồng bộ, standby chỉ đọc, replication lag và vấn đề "vừa ghi xong đọc ở replica không thấy"; failover (Patroni); logical replication (publication/subscription) để nâng cấp phiên bản hoặc chia sẻ một phần bảng.
  5. Partitioning: khai báo (RANGE theo tháng cho giao dịch, LIST, HASH); partition pruning; index trên bảng partition; dọn dữ liệu cũ bằng DETACH/DROP PARTITION thay vì DELETE hàng tỷ dòng.
  6. Phân quyền: role, GRANT/REVOKE; tách owner / migration / ứng dụng / chỉ đọc; default privileges; Row-Level Security cho phân quyền theo chi nhánh hoặc tenant.
  7. Bảo vệ dữ liệu nhạy cảm: TLS cho connection (sslmode=verify-full); mã hoá ở đĩa; mã hoá cột (pgcrypto, hoặc mã hoá ở ứng dụng với khoá trong KMS/HSM — thường ưu tiên); masking cho môi trường test; không log dữ liệu cá nhân; PCI DSS (không lưu CVV); Luật Bảo vệ dữ liệu cá nhân 2025 và Nghị định 356/2025.
  8. PgBouncer khi nhiều instance ứng dụng (transaction mode và giới hạn của nó).
  9. Theo dõi cơ bản: pg_stat_activity, chuỗi chặn khoá (pg_blocking_pids), dung lượng, replication lag, autovacuum.

Vì sao thứ tự này: migration trước (developer làm hằng ngày) → đổi schema an toàn (nơi migration gây sự cố production) → backup (bảo vệ trước khi mở rộng) → replication (sẵn sàng cao, tách đọc) → partition (dữ liệu lớn dần) → phân quyền và bảo mật (yêu cầu kiểm toán của ngân hàng) → pooler và theo dõi.

Giai đoạn 9 — Mở rộng: Redis, NoSQL, OLAP (tuần 23–24)

Mục tiêu: biết khi nào PostgreSQL là đủ, khi nào thêm một kho lưu trữ khác, và dùng Redis đúng cách.

Chủ đề theo thứ tự

  1. Vì sao không chỉ PostgreSQL: những mẫu truy cập RDBMS không tối ưu — độ trễ micro-giây, tìm kiếm mờ trên văn bản, phân tích trên hàng tỷ dòng, dữ liệu cấu trúc rất thay đổi.
  2. Redis: key-value trong bộ nhớ; kiểu dữ liệu (string, hash, list, set, sorted set, stream); TTL; dùng cho cache, session, rate limit, khoá phân tán (cẩn thận), bảng xếp hạng, idempotency key tạm; lưu xuống đĩa RDB/AOF; eviction; lệnh thực thi trên một luồng chính. Giấy phép: Redis 8 thêm AGPLv3; Valkey là nhánh mã nguồn mở do Linux Foundation quản lý.
  3. Mẫu cache: cache-aside, write-through, write-behind; vô hiệu hoá; stampede, avalanche, penetration; cache không bao giờ là nguồn sự thật của số dư.
  4. Các họ NoSQL: document (MongoDB), key-value (Redis, DynamoDB), wide-column (Cassandra), tìm kiếm (Elasticsearch/OpenSearch), graph, time-series — đánh đổi giữa schema linh hoạt và ràng buộc, scale ngang và transaction.
  5. CAP, nhất quán mạnh vs nhất quán cuối cùng (eventual consistency) — đủ để so sánh các lựa chọn.
  6. OLTP vs OLAP: lưu theo dòng vs theo cột; ClickHouse, BigQuery, Snowflake, DuckDB; vì sao không chạy báo cáo nặng trên database giao dịch → replica hoặc CDC sang kho phân tích.
  7. CDC và outbox: Debezium đọc WAL; transactional outbox để "ghi database + phát sự kiện" nhất quán.
  8. Cái giá vận hành: mỗi kho thêm là thêm backup, giám sát, bảo mật, đồng bộ. PostgreSQL làm "đủ tốt" nhiều việc (jsonb, full-text, pg_trgm, partition, SKIP LOCKED làm hàng đợi).

Vì sao thứ tự này: Redis trước (thứ hay được thêm vào stack Spring Boot nhất và bị hỏi ở mọi vòng backend) → mẫu cache (dùng sao cho đúng) → bức tranh NoSQL → lý thuyết nhất quán để so sánh → OLTP/OLAP → CDC/outbox (dữ liệu đi giữa các kho thế nào) → khung quyết định.

Bài tập

  1. Thêm Redis vào docker compose; cache-aside cho "biểu phí" của mini-bank — đo độ trễ trước/sau; vô hiệu hoá khi admin sửa biểu phí; cố tình gây stampede (TTL hết cùng lúc) rồi sửa (jitter hoặc khoá).

  4. MongoDB vs jsonb: lưu "hồ sơ yêu cầu bồi thường" có cấu trúc thay đổi theo sản phẩm bảo hiểm — chọn gì, vì sao.
